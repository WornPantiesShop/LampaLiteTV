# Lampa Lite TV 1.5.7: Online Mod, HDRezka cookies and diagnostics

Added the requested fourth extension http://nb557.surge.sh/online_mod.js.
A separate one-time migration preserves previous manual disable/removal choices
for the original three extensions. Accounts are configured only on the user's TV;
no account identifiers, passwords or session cookies are bundled in source/APK.

## HDRezka compatibility

The ordinary Android Lampa host supports native HTTP requests and response cookies.
The lightweight WebView host did not: the plugin's browser login was rejected by
CORS (MissingAllowOriginHeader). Merely adding an input or setting a success flag
would not authenticate an account.

The new jQuery transport is restricted to HTTPS kvk.zone and rezka.ag. Other URLs
retain their original transport. It uses an opaque random 128-bit request ID in
a custom navigation scheme; no credentials/cookies enter URLs. The host accepts
only main-frame calls from the Lampa page and obtains the request from its pending
map. No AndroidJS platform impersonation, general JavaScript native HTTP interface,
TLS bypass or WebView CORS/security flag changes were added.

Native policy is checked again: no userinfo/explicit ports; GET or POST only, with
POST restricted to /ajax/login/ and /ajax/get_cdn_series/. Redirect destinations
are revalidated (maximum five hops). URL/body limits are 8 KiB/64 KiB, response
limit is 4 MiB after gzip decompression, network timeouts are 8 seconds. A single
background worker has a bounded queue and is shut down with the Activity.

Login omits old session cookies, matching the ordinary app's fresh-cookie flow;
otherwise the server rejects re-login to an already authenticated session.
Subsequent requests use saved provider cookies and a consistent user agent.
Gzip is handled, including a server that sends it despite an identity preference.
Cookie headers reject CR/LF and excessive length. Sensitive request/response data
is not logged. Cookies stay in the plugin's existing storage and the app cookie jar.

The regular Online Mod login handler is retained. Cookie input and Fill Cookies
controls are added for the lightweight host, which remains in browser mode for
other integration features. Filling uses the same real login handler.

## Performance work

The menu observer no longer watches header mutations; settings cleanup uses the
settings-open event. Catalog animation/layout CSS and row visibility were not changed.
A native-input CPU profile with four extensions showed roughly 230 ms in
getBoundingClientRect and 66 ms self-time in frameVisible over about 23 seconds.
Most samples were idle or native program work; this profile does not by itself
identify a GPU bottleneck. Disabling catalog motion is not supported by this evidence.

The same 24-key native-input scenario is measured using benchmark-c645.ps1 and
diagnose-c645.ps1. Presentation FPS and per-key 400 ms windows are reported separately
from JS RAF callbacks. Short, non-randomized runs and changing server/cache/catalog
state limit causal conclusions. A locked 60 FPS is not claimed.

| Capture | Navigation presentation FPS | p95 interval ms | intervals >25ms / samples |
|---|---:|---:|---:|
| Before, four extensions | 55.31 | 33.31 | 42 / 507 |
| After, initial | 55.73 | 33.33 | 38 / 508 |
| After, warm | 58.15 | 17.76 | 16 / 533 |

All three runs recorded 24 keys and ended in items_line. Device monotonic uptime
reset between the before and after captures; current boot reason was cold.
No reboot command was issued by this task. The runs therefore do not establish
an improvement caused by this patch. The warmed result is close to the target,
but occasional missed frames remain. Raw captures and account data are not in Git.

Provider login/cookie success is not a test of every film, CDN, payment entitlement
or external player. Other provider requests remain on their existing browser path.
